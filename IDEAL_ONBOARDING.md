# Stripe Connector — идеальный первый запуск (целевая картина)

Источник методологии: `Docs/session-notes/ONBOARDING_FIRST_LAUNCH_STANDARD.md`.
Основано на `POST_CONNECT_EXPERIENCE.md` этого приложения (целевой пользователь:
финансовый директор/founder SaaS/e-commerce бизнеса).

## 1. Credential type
API key (Secret Key или Restricted Key, одно поле, `AUTH_AND_CREDENTIALS_STANDARD.md`
класс "статический API key"). Есть Live/Test режим — критично отличать визуально.

## 2. Идеальный флоу (не ограничен текущим SDK)

1. **Первое открытие** — сайдбар сразу показывает `Badge("Не подключено")` +
   однострочно: "Подключите Stripe, чтобы видеть выручку, платежи и подписки
   прямо здесь". Центр — `Empty` с тем же CTA.
2. **Клик "Connect Stripe"** — идеально: живой inline-виджет выбора Live/Test
   режима ДО ввода ключа (переключатель), с разными плейсхолдерами
   (`sk_live_...` / `sk_test_...`) и явным предупреждением, если вставлен ключ
   не того формата, что выбранный режим — ПРЯМО в момент ввода (client-side
   валидация по префиксу), не после отправки на сервер.
3. **Во время проверки ключа** — идеально: пошаговый живой прогресс: "Проверяем
   ключ… → Читаем баланс… → Загружаем последние платежи…", а не единственный
   спиннер "Проверяем…".
4. **После успеха** — идеально: сразу видно баннер режима (Live/Test) как
   постоянный элемент шапки приложения (не только в сайдбаре), чтобы нельзя было
   случайно принять решение по возврату/refund, глядя на тестовые данные.
5. **Multi-account** — если у пользователя несколько Stripe-аккаунтов
   (агентство с несколькими клиентами) — идеально: выбор аккаунта через
   переключатель прямо в шапке, с быстрым сравнением балансов между ними в одном
   списке до выбора активного.
6. **Ошибка** — идеально: если ключ Restricted (не Secret) и не хватает
   permissions на конкретный ресурс — узнать это ДО первого реального вызова API,
   через явный dry-run список permissions ключа (Stripe API это поддерживает
   частично — `GET /v1/account` не всегда фейлится там, где упадёт конкретный
   ресурс) и явно перечислить, каких permissions не хватает.

## 3. Известные ограничения SDK, которые НЕ дают это сделать буквально сегодня

- Нет client-side JS-валидации по мере ввода (SDK не даёт `on_change`
  промежуточную валидацию без полного round-trip на сервер) → L1-класс
  ограничения. Обходной путь: валидация по префиксу ключа делается на сервере
  при submit, ошибка — сразу в форму.
- Нет пошагового live-прогресса с текстом (нет `Stepper`, см. L4) → эмулируется
  одним `loading_label="Проверяем ключ…"` на кнопке Submit.
- Постоянный баннер режима "снаружи" панели (в шапке хоста) — вне контроля
  приложения; реализуемо ТОЛЬКО внутри left-сайдбара как всегда видимый Text/Badge.
- Dry-run permissions ключа — Stripe API не отдаёт полный список permissions
  restricted-ключа единым вызовом; узнаём по факту первого реального отказа
  (403 на конкретном ресурсе) — честно фиксируется как ограничение провайдера,
  не SDK.
